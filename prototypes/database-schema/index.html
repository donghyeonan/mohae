Life Lab은 두 독립 도구를 한 앱에 둔다

Me는 측정과 시간 이해를, Explore는 세상의 가능성 발견과 경험 기록을 담당한다. 현재 두 데이터 흐름은 서로를 읽거나 갱신하지 않는다.

경계 교정

이전 문서는 Me와 Explore를 하나의 폐쇄 루프로 연결해 현재 구현보다 앞선 인과관계를 주장했다. 둘은 같은 앱과 사용자 계정에 있을 뿐, 현재는 독립된 bounded context다.

현재 제품 경계

Life Lab은 독립적으로 쓸 수 있는 두 도구를 하나의 앱과 계정 안에 배치한다.

Me

사용자가 원하는 측정 항목을 정의하고 명시적으로 기록한다. 실제 시간 사용을 보며 시간의 희소성을 이해한다.

Explore

현실의 장소·상품·행사를 Random 또는 Preference로 발견하고, 앱 반응과 실제 경험을 별도로 기록한다.

현재 계약 — 두 context는 앱 껍데기의 auth.users와 user_profiles만 공유한다. Me 측정과 Explore 활동은 상호 참조하지 않으며, 연결점은 실제 사용 중 구체적인 필요가 발견될 때 별도 계약으로 추가한다.

03. Explore / Delivery — 두 모드만 시작한다

v0는 복잡한 개인화 모델 없이 같은 추출기의 가중치만 바꾼다. 여기서 ‘유효한 catalog’는 폐점·종료·잘못된 정보가 아닌 현실의 후보 전체이며, Random에는 지역·목표·취향 gate를 적용하지 않는다.

random

모든 유효 후보의 weight를 동일하게 둔다. 서울 사용자에게 제주 쉐어하우스가 나오는 것도 의도된 동작이다.

preference

저장·실제 경험한 카드와 공통 tags가 있으면 weight를 올린다. 일치하지 않는 후보도 0으로 만들지 않는다.

최소 알고리즘 — Random은 균등 추출, Preference는 Explore 내부 저장·경험만 사용하는 단순 weighted random이다. Me 데이터, collaborative filtering, embedding, ML ranker는 현재 계약에 없다.
DELIVERY · SOURCE OF TRUTH추천 후보가 아니라 실제 발행 사실
recommendation_batches기간별 사용자 덱

Random 또는 Preference 모드, 선택 시점, 유효 후보 수를 보존한다. policy_version이 유효성 규칙을 식별한다. 정확한 후보 목록 재현은 temporal catalog가 필요한 후속 요구로 남긴다.

user_idmodeeligible_countcatalog_as_ofstarts_atends_atpolicy_versionissued_at
recommendation_instances사용자별 추천 사실

몇 번째 추출에서 어떤 카드가 선택됐는지와 그 순간의 조건부 선택 확률을 남긴다. Random 데이터가 Preference의 자기강화 편향을 비교하는 기준이 된다.

Event 순서는 서버가 결정한다

occurred_at은 기기 시각이며 현실에서 행동한 때를 표시할 뿐이다. clock skew·오프라인 전송·동시 입력 때문에 현재 상태 replay 순서로 사용할 수 없다.

event_seqcanonical replay order
server assigned
  1. 클라이언트가 안정적인 client_event_id와 행동 시각 occurred_at을 보낸다.
  2. PostgreSQL RPC가 인증·불변식을 검증한다.
  3. 서버 sequence가 단조 증가 event_seq를 부여한다.
  4. 서버가 recorded_at = clock_timestamp()를 기록한다.
  5. (user_id, client_event_id)가 같으면 같은 요청은 기존 event를 반환하고, payload가 다르면 거부한다.
  6. 현재 저장·숨김 상태는 event_seq 순서로만 계산한다.

구분: occurred_at = 사용자가 행동했다고 주장한 현실 시각, recorded_at = DB 수락 시각, event_seq = 상태 전이의 유일한 총순서. sequence gap은 rollback 때문에 허용한다.

Tenant 소유권도 DB가 강제한다

user_id를 중복 저장하는 이유는 직접 RLS와 인덱스를 적용하기 위해서다. 하지만 복제값을 신뢰하지 않고, 모든 user_id는 auth.users를 참조하며 아래 composite FK로 부모와 같은 사용자인지 다시 강제한다.
